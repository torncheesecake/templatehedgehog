# Template Hedgehog soft-launch checklist

Use this checklist before sending Template Hedgehog to prospects or a small paid audience. The goal is soft-launch confidence, not full public-scale proof.

## Homepage

- [ ] The first viewport explains that Template Hedgehog is a production email workflow system, not a template marketplace.
- [ ] The hero artefact clearly shows source, review, compile, QA, and handoff.
- [ ] The page answers what the buyer receives before asking them to compare pricing.
- [ ] Trust sections show sample pack, QA proof, delivery flow, licence clarity, and update access.
- [ ] No price-led CTA appears before the visitor understands the product.

## Pricing

- [ ] Core, Pro, and Team are immediately distinguishable.
- [ ] Pro is clearly the main paid purchase path.
- [ ] Team is explained as rights, rollout, support, and longer updates, not more templates.
- [ ] The licence matrix is readable on desktop and mobile.
- [ ] Buy Pro remains directly purchasable.

## Checkout

- [ ] Stripe checkout opens for Pro.
- [ ] Core and Team behaviour matches intended commercial handling.
- [ ] The success page explains what has been purchased.
- [ ] The signed download path works for the matching archive.
- [ ] Failed download guidance points to support with the required purchase details.

## Sample pack

- [ ] The public sample pack downloads successfully.
- [ ] The sample pack contains MJML source, compiled HTML, QA notes, preview reference, testing proof, implementation guide, archive structure, and licence reference.
- [ ] The sample content is representative enough to reduce uncertainty without exposing the paid archive.
- [ ] The sample pack link is reachable from homepage and pricing proof sections.

## Docs

- [ ] Docs are calm, readable, and technical.
- [ ] Docs explain source vs compiled HTML.
- [ ] Docs explain snippet vs standalone mode.
- [ ] Docs include Outlook, image-hosting, ESP handoff, and common pitfall guidance.
- [ ] Docs do not read like marketing copy.

## Downloads

- [ ] Public sample download returns a zip file.
- [ ] Paid archive download is private and signed.
- [ ] Archive folder structure is documented publicly.
- [ ] Version and changelog metadata are visible inside the archive.
- [ ] File names are understandable to a buyer after purchase.

## Support flow

- [ ] Support page covers implementation, download, and licence fit.
- [ ] Support email is visible and clickable.
- [ ] Refund and delivery reassurance are clear before purchase.
- [ ] Licence questions route buyers to support before buying Team.
- [ ] NetSuite service remains a quiet secondary support path, not the main product path.

## Founder proof

- [ ] About page explains why the product exists.
- [ ] Founder proof is based on real HTML email production experience.
- [ ] Copy does not invent customers, testimonials, logos, or case studies.
- [ ] The product origin connects repeated email patterns to editable MJML, compiled HTML, QA, and handoff.
- [ ] Trust proof links to the founder proof section.

## Mobile QA

- [ ] Homepage hero stacks cleanly.
- [ ] Product artefact remains readable or simplifies without overflow.
- [ ] Pricing cards remain scannable.
- [ ] Licence matrix can scroll horizontally without breaking layout.
- [ ] Component and layout detail previews do not create horizontal scroll.
- [ ] Code panels remain usable on small screens.

## Purchase journey

- [ ] A cold buyer can go from homepage to pricing to sample pack without confusion.
- [ ] The buyer can answer: what is it, what do I receive, why Pro, what happens after purchase.
- [ ] The buyer understands commercial usage limits before buying.
- [ ] There are no disabled purchase states that look broken.
- [ ] The product feels credible enough for a soft launch despite no customer proof yet.

## Soft-launch decision

- [ ] No launch-blocking checkout or download issues remain.
- [ ] No obvious visual regressions remain on homepage, pricing, components, layouts, docs, support, about, or changelog.
- [ ] Founder proof is live.
- [ ] Sample pack is accessible.
- [ ] Support and refund reassurance are accessible before purchase.

Decision:

- Ready for soft launch when every purchase-path item is checked.
- Continue refining before broad launch until customer proof, real usage feedback, and at least one case-study placeholder can be replaced with evidence.
